# Персональный ассистент — лабораторная по «AI в разработке ПО»

Консольный ассистент получает поручение, изучает выбранные текстовые файлы
через инструменты и сохраняет отчёты. Он умеет выполнять цепочки скиллов
и строить план такой цепочки по свободному запросу с помощью локальной модели.
Агентный цикл, исполнитель этапов и планировщик написаны самостоятельно,
на стандартной библиотеке Python.
В репозитории находятся код, тесты и вымышленные учебные примеры.
Личные настройки `.env`, материалы лекций, реальные проекты, журналы и отчёты
запусков в публикацию не входят; для настроек предусмотрен `.env.example`.

Описание понятий с аналогиями и примерами: [теория работы ассистента](docs/THEORY.md).
Перечень изменений относительно первой опубликованной версии: [CHANGELOG.md](CHANGELOG.md).

## Первый запуск без модели

Нужен Python 3.11 или новее. Дополнительные библиотеки устанавливать не требуется.
В PowerShell, из папки проекта:

```powershell
python -m assistant_lab --demo
```

Это **сценарная имитация модели**, а не работа нейросети. Она использует тот же
харнесс и настоящие файловые инструменты: читает `workspace/project/README.md`,
сохраняет в отчёт выдержку из документа и возвращает итоговый ответ.
Демо не обращается к сети. Оно нужно для знакомства с устройством программы.

В конце программа напечатает абсолютные пути к результатам:

- `workspace/reports/<идентификатор запуска>/report.md` — отчёт;
- `runs/<идентификатор запуска>.jsonl` — журнал событий.

Каждый запуск получает отдельную папку. Предыдущие отчёты не перезаписываются.
Входной README описывает вымышленный проект Study Planner и явно указывает,
что рабочее приложение планировщика пока не реализовано.

## Подключение локальной модели через Unsloth Studio

Этот этап можно выполнить позже, когда вы решите запустить модель.
Прототип ожидает локальный **OpenAI-compatible Chat Completions API**.

1. В вашей версии Unsloth включите API и загрузите модель, поддерживающую
   вызовы инструментов (`tools` / function calling). Одного обычного чата
   недостаточно: сервер должен возвращать структурированные `tool_calls`.
2. Скопируйте `.env.example` в `.env`, если своего файла настроек ещё нет:

   ```powershell
   Copy-Item -LiteralPath .env.example -Destination .env
   ```

3. Заполните в `.env` адрес сервера и точное имя модели:

   ```dotenv
   ASSISTANT_BASE_URL=http://127.0.0.1:8000/v1
   ASSISTANT_MODEL=имя-модели-из-вашего-API
   ASSISTANT_API_KEY=
   ```

   **Порт 8000 здесь только пример.** Возьмите адрес из вашего Unsloth.
   Базовый адрес заканчивается на `/v1`, без `/chat/completions`.
   Если сервер не требует ключ, оставьте `ASSISTANT_API_KEY` пустым.
   Настоящие ключи не нужно присылать в чат или добавлять в репозиторий.

4. Проверьте соединение и получите список точных имён моделей:

   ```powershell
   python -m assistant_lab --check
   ```

   Для этой команды достаточно `ASSISTANT_BASE_URL`; имя модели можно
   заполнить после получения списка. Проверка делает `GET /v1/models`.
   Успешный ответ ещё не подтверждает поддержку инструментов.

5. Запустите стандартное поручение с настоящей моделью:

   ```powershell
   python -m assistant_lab
   ```

   Ассистент попросит модель прочитать README, составить краткое описание
   назначения, возможностей и ограничений проекта и сохранить отчёт.

Можно передать своё поручение или выбрать другую папку учебных документов:

```powershell
python -m assistant_lab "Прочитай README.md и сохрани отчёт: что уже есть и что ещё предстоит сделать."
python -m assistant_lab --project .\workspace\project --source README.md
```

В деморежиме используется только фиксированный учебный сценарий;
произвольное поручение доступно при подключении настоящей модели.

CLI-параметры имеют приоритет над переменными окружения, а переменные
окружения — над `.env`. Все настройки проекта имеют префикс `ASSISTANT_`.
Файл `.env` читается как буквальные пары `KEY=VALUE`, без выполнения команд
и без подстановки переменных. Полный список параметров:

```powershell
python -m assistant_lab --help
```

Описание возможностей API Unsloth: <https://unsloth.ai/>.
Формат протокола: <https://developers.openai.com/api/docs/guides/function-calling>.
Совместимость конкретной установленной версии и модели необходимо проверить
при живом запуске; программа не запускает и не обновляет Unsloth самостоятельно.

## Поручения и скиллы

Скилл — сохранённая инструкция о том, как выполнять определённый вид поручений.
Он задаёт порядок действий и требования к результату. Функцию `read_file`
по-прежнему выполняет Python-код; скилл объясняет модели, когда и зачем её вызвать.
Сейчас в библиотеке три скилла:

- `project-review` — частичный обзор назначения, структуры и компонентов проекта;
- `compare-documents` — сравнение двух явно указанных текстовых документов.
- `compare-materials` — сопоставление двух или более материалов по единым критериям,
  в том числе готовых обзоров проектов; без обязательного отношения «старая/новая версия».

Обычное поручение можно написать своими словами. Замените пути и имена файлов
в примерах своими:

```powershell
python -m assistant_lab --project .\my_project "Объясни назначение проекта, его основные компоненты и сохрани обзор."
python -m assistant_lab --project .\my_docs "Сравни requirements-v1.md и requirements-v2.md, сохрани отчёт о различиях."
```

Готовый небольшой пример сравнения уже находится в `workspace/documents`:

```powershell
python -m assistant_lab --project .\workspace\documents "Сравни requirements-v1.md и requirements-v2.md и сохрани отчёт."
```

Модель получает имена и краткие описания доступных скиллов. Для подходящего
поручения она выбирает скилл через `load_skill`; программа загружает его инструкции
в контекст. Тела всех скиллов заранее в каждое поручение не добавляются.
Выбор зависит от ответа модели, а не от поиска фиксированных ключевых слов
в русском предложении. Если нужны конкретные инструкции, скилл можно выбрать явно:

```powershell
python -m assistant_lab --skill project-review --project .\my_project "Обрати внимание на конфигурацию и основные компоненты."
python -m assistant_lab --skill compare-documents --project .\my_docs "Сравни requirements-v1.md и requirements-v2.md."
```

Один обычный запуск активирует один скилл; смена внутри этапа запрещена. При
автоматическом выборе `load_skill` расходует обычный вызов инструмента и шаг
модели. Загрузка фиксируется в журнале событием `skill_loaded` с именем скилла;
тексты инструкций в журнал не записываются.

При `--skill` программа загружает выбранные инструкции сразу, без отдельного
шага модели на выбор. Дальнейшее выполнение всё равно требует подключённой модели.
`--describe-project` сохранён как короткая совместимая команда выбора
`project-review`. `--demo` и `--check` работают как раньше. Список имён и описаний
можно посмотреть без модели, сети и чтения `.env`:

```powershell
python -m assistant_lab --list-skills
```

Для `compare-documents` нужны два однозначных пути относительно `--project`,
для `compare-materials` — явно указанный список из двух или более файлов. Если их
не хватает, ассистент должен попросить указать файлы, а не угадывать пару.
В таком случае вопрос печатается в терминале, отчёт ещё не создан, а программа
завершается с кодом `1` как при неполном поручении. Повторите поручение со всеми нужными
путями в новом запуске: внутри одного запуска интерактивного диалога нет.
Все нынешние скиллы предназначены для подготовки отчёта; штатный успех CLI
требует его фактического сохранения. Для сравнения программа дополнительно
проверяет, что были успешно прочитаны два разных файла. Если прочитаны только
фрагменты, результат должен называться частичным сравнением. Отсутствие
изменения в просмотренных строках не доказывает, что остальные строки одинаковы.

Библиотека инструкций находится внутри модуля:

```text
assistant_lab/skill_library/
    project-review/SKILL.md
    compare-documents/SKILL.md
    compare-materials/SKILL.md
```

Автор проекта меняет эти файлы, чтобы уточнить рецепты. Для нового скилла
добавьте папку `assistant_lab/skill_library/my-skill/` с файлом `SKILL.md`:

```markdown
---
name: my-skill
description: Краткое описание того, для каких поручений нужен этот скилл.
---

# Инструкция

Опишите шаги работы, доступные инструменты и требования к результату.
```

Наш runtime поддерживает небольшой формат: однострочные `name` и `description`
между разделителями `---`, затем Markdown с инструкциями. `name` записывается
обычным именем kebab-case без кавычек; `description` может быть обычной строкой
или однострочной строкой в JSON-кавычках. Это собственная
реализация загрузки инструкций, без обещания поддержки всей спецификации Agent Skills.
Основа формата описана в [официальной спецификации](https://agentskills.io/specification).
Дополнительные YAML-поля и сложные YAML-конструкции не поддерживаются и приводят
к отклонению скилла. Описание нужно для выбора моделью; автоматические тесты
проверяют протокол выбора и загрузки, но не оценивают качество выбора настоящей моделью.
Файлы `SKILL.md` включаются в устанавливаемый пакет через `pyproject.toml`.

Каталог скиллов контролирует автор приложения. Файлы изучаемого проекта не
становятся скиллами автоматически, а найденные внутри них команды остаются
недоверенными данными. Скиллы не добавляют прав, не исполняют скрипты и не
подключают MCP. Доступ к исходникам, запрет их изменения и ограничения чтения
по-прежнему обеспечивает код инструментов.

## Описать проект по текстовым файлам

Для выборочного обзора проекта можно явно выбрать скилл короткой командой.
Например, из текущей папки:

```powershell
python -m assistant_lab --describe-project --project .\workspace\project
```

Unsloth и API должны быть уже запущены, настройки берутся из вашего `.env`.
Для собственного проекта замените `.\workspace\project` путём к его папке.
Если запускаете команду из другой папки, укажите абсолютный путь к проекту.
Переносить исходники в `workspace/project` или писать README специально для
ассистента не требуется. `--source` относится к прежнему сценарию одного документа.

Для работы с материалами доступны три инструмента: `list_files`, `read_file`, `save_report`.
`list_files(path=".", offset=0, limit=100)` выдаёт страницу списка файлов
выбранного подкаталога, включая вложенные папки в пределах ограничений обхода.
Все возвращённые пути относительны корню проекта. Модель может запросить
следующую страницу по `next_offset` или сосредоточиться на нужном подкаталоге.
В ответе есть `files` с путями, размерами и признаком `readable`, а также
`truncated`, `scanned` и `remaining_read_bytes`. Один запрос просматривает
не более 2000 записей и ограничивает глубину обхода 20 уровнями.
`readable` при листинге означает допустимое имя и размер; содержимое и кодировка
проверяются при чтении. Если `truncated=true`, но `next_offset=null`, достигнут
предел обхода: страницы не позволяют получить ещё не просканированные записи.
Весь каталог автоматически в контекст не загружается.

Режим подходит для текстовых файлов разных стеков: документов, конфигурации,
исходников и сценариев. Модель выбирает стек по найденным файлам и их содержимому:
например, `pom.xml` или Gradle для Java, `pyproject.toml` для Python,
`package.json` для JavaScript, `go.mod` для Go, `Cargo.toml` для Rust,
`.csproj` для .NET, `CMakeLists.txt` для C/C++. Расширения не образуют закрытый
список: файл без расширения или с неизвестным расширением тоже может оказаться
текстовым. Библиотека и монорепозиторий могут иметь несколько способов запуска
или вообще не иметь одной исполняемой точки входа.

`read_file(path, start_line=1, max_lines=200)` читает фрагмент файла. Ответ
содержит `content`, `path`, `start_line`, `end_line`, `truncated`, `next_line`
и остаток бюджета `remaining_read_bytes`. `max_lines` допускает от 1 до 500 строк.
При наличии продолжения модель использует `next_line`. Фрагмент заканчивается
на границе строки; если первая запрошенная строка не помещается в доступный
бюджет, инструмент возвращает ошибку. Поддерживаются UTF-8 и текст с BOM в UTF-16/UTF-32.
Полученный фрагмент передаётся локальной модели как материал текущего поручения;
это не переобучение модели. Прочитанные строки не доказывают, что изучен весь файл.

Большинство скрытых каталогов, `.git`, типичные файлы ключей и секретов,
настройки IDE, зависимости и результаты сборки исключаются. Исключения для
скрытых каталогов — `.github` и `.gitlab`. Из точечных файлов явно допускаются
`.gitignore`, `.gitattributes`, `.editorconfig`, `.dockerignore`, `.prettierrc`
и `.eslintrc`, а также предусмотренные политикой варианты двух последних
с расширениями конфигурации. `.env` и его варианты исключаются.
Картинки, архивы, исполняемые файлы и другое бинарное содержимое не читаются.
Ограничения действуют и при прямом запросе `read_file`, а не только при листинге.
Фильтр имён и типов не обнаруживает секрет, случайно записанный в обычном исходнике.

Для чтения рассматриваются файлы до 2 МиБ, а один возвращаемый фрагмент ограничен
64 КиБ. Общий бюджет выданного текста — **16 КиБ на запуск**, включая повторное
чтение. Его можно изменить параметром `--read-budget` или настройкой
`ASSISTANT_READ_BUDGET` в байтах, максимум — 1 МиБ:

```powershell
python -m assistant_lab --describe-project --project .\workspace\project --read-budget 32768
```

Увеличение бюджета не увеличивает контекстное окно модели. История запросов,
схемы инструментов и генерируемый отчёт тоже занимают токены. При исчерпании
бюджета агент должен закончить обзор по уже полученным материалам.
Список файлов и глубина обхода также ограничены; неполная выдача не подтверждает
отсутствие других файлов.

Это **частичный статический обзор выбранных фрагментов**, а не полный обход
проекта. Для другого поручения можно выбрать другую папку или увеличить бюджет;
увеличение само по себе не гарантирует полного покрытия. Агент не собирает и
не запускает проект. В отчёте он должен отделять объявленные настройки от
проверенного поведения, указывать пути и диапазоны строк, подтверждающие выводы.
Сохранение разрешается после успешного листинга и чтения хотя бы одного файла.
Программа добавляет в конец отчёта фактические источники и печатает прочитанные
пути в терминале. Перечень источников не означает, что файлы прочитаны целиком.

Отчёт и журнал сохраняются в обычных `workspace/reports/<run>/` и `runs/`.
Инструмента изменения исходного проекта у агента нет.
Можно добавить пожелание к обзору:

```powershell
python -m assistant_lab --describe-project --project .\workspace\project "Обрати внимание на назначение компонентов и настройки запуска."
```

## Цепочка: описать проекты и сравнить

Команда `--compare-projects` выполняет несколько связанных этапов. Укажите
от двух до четырёх разных папок, повторив `--project` для каждой:

```powershell
python -m assistant_lab --compare-projects --project .\workspace\project --project .\workspace\project_library
```

Обе папки содержат вымышленные описания, а не готовые приложения. Для реальных
проектов подставьте свои пути. Модель и локальный API должны быть запущены.
Можно добавить пожелание ко всей цепочке:

```powershell
python -m assistant_lab --compare-projects --project .\my_project_a --project .\my_project_b "Сравни назначение, структуру и подтверждённые возможности."
```

Исполнение устроено так:

1. Приложение строит план `project-1 → project-2 → … → comparison`.
2. Для каждого проекта запускается `project-review` с отдельной историей,
   корнем файлового доступа и отчётом. Другие проекты в его инструменты не входят.
3. Приложение передаёт точные снимки успешных отчётов в новую входную папку.
4. Новый этап использует общий скилл `compare-materials`. Он получает только
   эти отчёты и соответствие их идентификаторов исходным проектам.
5. Сравнение сохраняется после полного чтения всех переданных отчётов.

В этой команде план выбирает приложение: это готовая последовательность.
Построение плана моделью включается отдельной командой `--auto-plan`, описанной ниже.
Внутри каждого этапа
файлы и вызовы инструментов выбирает модель. Скиллы заранее назначены этапам,
поэтому дополнительный вызов `load_skill` здесь не нужен.

Исполнитель `WorkflowRunner` в `assistant_lab/workflows.py` не привязан к этому
сценарию. Его `WorkflowStep` задаёт имя этапа, скилл, поручение и либо одну папку
источников, либо список предыдущих этапов. Для следующего сценария можно составить
другой план из имеющихся скиллов. Поддерживаются до восьми последовательных
этапов; зависимости должны ссылаться на уже выполненные этапы. Смешивание
исходной папки с зависимостями пока не поддерживается. Смена скилла внутри
одного этапа и параллельное выполнение не добавлены.

Для двух проектов результаты расположены так:

```text
workspace/reports/<run>/
    project-1/report.md
    project-2/report.md
    comparison/inputs/project-1.md
    comparison/inputs/project-2.md
    comparison/report.md
```

В `inputs` находятся обычные копии снимков отчётов, без ссылок на исходники.
Финальный этап не получает историю обзоров, исходники или права чтения других
папок. Источники сравнительного отчёта ссылаются на входные обзоры; источники
самих обзоров — на выбранные фрагменты исходных проектов.

Ошибки модели, исчерпание лимитов и отсутствие подтверждённого отчёта
останавливают цепочку. Даже сохранённый отчёт при последующей ошибке этапа
не передаётся дальше. Уже созданные отчёты остаются для проверки. Успешное
завершение всей цепочки требует успеха каждого этапа.

`--max-steps` и `--max-tool-calls` действуют **на каждый этап**; по умолчанию
это восемь запросов модели и восемь вызовов инструментов. Для четырёх проектов
получается пять этапов и максимум 40 запросов модели при настройках по умолчанию.
В конце CLI печатает общие счётчики. `--read-budget` ограничивает каждый обзор
исходников отдельно. Для сравнения бюджет автоматически равен полному размеру
входных отчётов: в CLI не более четырёх файлов по 64 КиБ. Повторное чтение тоже
расходует этот бюджет. Большой вход всё равно может не поместиться в контекст
конкретной модели; лимит байтов не увеличивает её контекстное окно.

Перед сохранением сравнения Python-код проверяет покрытие всех строк каждого
обязательного отчёта. Повторное чтение одной части или чтение только начала
и конца не закрывает пропущенную середину. Это подтверждает получение отчётов,
а не истинность их содержания: сами обзоры остаются частичными и могут содержать
ошибки модели. Неописанная возможность не считается отсутствующей.

В одном журнале появляются события `workflow_started`, `stage_started`,
`stage_finished`, `workflow_finished` с именами этапов, статусами и счётчиками.
Содержимое отчётов, поручения и пути исходных проектов в журнал не записываются.

## План по свободному поручению

В режиме `--auto-plan` та же локальная модель сначала предлагает план из
доступных скиллов, затем выполняет проверенные этапы. Отдельную модель
загружать не требуется; адрес API, имя модели, ключ и параметры генерации
используются те же, что для обычной работы. История планирования отделена
от историй исполнения.

```powershell
python -m assistant_lab --auto-plan --project .\workspace\project --project .\workspace\project_library "Сначала опиши каждый из двух проектов, затем сравни их назначение и заявленные возможности."
```

Для одного проекта тоже можно строить план:

```powershell
python -m assistant_lab --auto-plan --project .\workspace\project "Подготовь краткий обзор проекта и сохрани его."
```

Разрешается от одной до четырёх папок. Они получают обозначения `project-1`,
`project-2` и далее в порядке параметров `--project`. Если папки имеют одинаковые
имена, используйте эти обозначения в поручении. Без `--project` доступна только
обычная папка `workspace/project`. Поручение обязательно.

Планировщик получает поручение, краткие описания скиллов и обозначения папок
с их именами. Содержимое проектов и полные инструкции всех скиллов заранее
не загружаются. Файловые инструменты во время планирования не предоставляются.

Модель возвращает JSON с этапами: скилл, подзадача, разрешённый проект либо
зависимости от предыдущих этапов. Приложение назначает безопасные имена
`step-1`, `step-2` и т. д. и проверяет весь план до исполнения:

- от одного до восьми этапов, только существующие скиллы;
- только переданные владельцем папки через `project-N`, без произвольных путей;
- зависимости от разных уже описанных этапов, без циклов и будущих ссылок;
- достаточное число входных отчётов: скиллу сравнения нужны хотя бы два;
- один источник входов: папка проекта либо отчёты зависимостей;
- ограниченный размер задач и отсутствие дополнительных полей с правами,
  командами, инструментами или новыми лимитами.

Исходное поручение сохраняется в заданиях этапов. Предложенная моделью
подзадача не может расширить файловые права или заменить системные правила.
Приложение не исполняет Python, shell или функции из JSON-плана.

После некорректного ответа допускается одна попытка исправить план: максимум
два обращения к модели на планирование. Исходный некорректный ответ и детали
исключений не добавляются в обратную связь и не попадают в журнал. При ошибке
подключения планирование завершается с понятным сообщением.
После начала исполнения план не перестраивается: при ошибке этапа цепочка
останавливается, сохраняя уже полученные отчёты для проверки.

Если имеющихся скиллов недостаточно или не хватает обязательных данных,
модель может вместо плана вернуть уточнение. Оно выводится в терминале;
этапы не запускаются, код возврата — `1`. Для продолжения повторите команду
с уточнённым поручением. Автоматического продолжения диалога пока нет.

Проверенный план печатается в кратком виде и сохраняется в
`workspace/reports/<run>/plan.json`, после чего выполняется. В JSON-плане есть
тексты заданий; он является локальным артефактом, исключённым из Git вместе
с остальными отчётами. Это не журнал событий и не формат импорта произвольного
плана для исполнения.

Результаты этапов находятся в `<run>/step-N/report.md`. Этап с зависимостями
видит только снимки их отчётов в собственной папке `inputs/step-N.md`.
CLI перечисляет все отчёты и отдельно результаты конечных этапов: их может
быть несколько, и произвольный план не обязан заканчиваться сравнением.

Запросы планировщика считаются отдельно и входят в общий итог обращений
к модели. `--max-steps` и `--max-tool-calls` по-прежнему ограничивают каждый
исполняемый этап; к ним добавляется максимум два запроса планирования.
Максимум при настройках по умолчанию — 8 × 8 + 2 = 66 обращений к модели.
Для этапов с зависимостями бюджет чтения равен размеру переданных отчётов;
ограничение контекстного окна конкретной модели всё равно сохраняется.

В журнал добавлены события `planning_started`, `planning_requested`,
`planning_rejected`, `planning_finished`. В нём остаются только статусы
и счётчики, без поручения и текста плана.

Структурно допустимый план может неверно отражать намерение пользователя.
Перед проверкой итоговых выводов полезно посмотреть сохранённый план.
Новые планы строятся из уже имеющихся возможностей: недостающий скилл или
инструмент по-прежнему нужно реализовать отдельно.

## Как устроен код

```text
__main__.py           Поручение, настройки и запуск
      ├─ planner.py   Запрос плана у модели, проверка JSON и привязка project-N
      ├─ workflows.py План этапов, отдельные контексты, передача отчётов
      ↓
agent.py              Харнесс: модель → инструмент → результат → следующий шаг
      ├─ skills.py    Каталог, описания и загрузка инструкций из skill_library
      ├─ skill_tools.py  load_skill и условия работы файловых инструментов
      ├─ providers.py Клиент локального API или сценарная DemoModel
      ├─ tools.py     read_file, save_report; в обзоре также list_files
      │    └─ file_policy.py  Отбор кандидатов и проверка текстовой кодировки
      └─ events.py    Журнал метаданных
```

Последовательность настоящего запуска:

1. Программа передаёт модели системную инструкцию, поручение и схемы инструментов.
2. Модель возвращает текст либо запрос инструмента.
3. Харнесс проверяет структуру запроса, имя инструмента и аргументы.
4. Обычный Python-код выполняет разрешённую файловую операцию.
5. Результат добавляется в историю с соответствующим `tool_call_id`.
6. Модель получает обновлённую историю. Цикл завершается итоговым ответом,
   ошибкой или достижением лимита.

История сообщений живёт в памяти в рамках одного этапа. Workflow передаёт
следующему этапу выбранные отчёты, а не всю историю сообщений. Долгосрочная
память, MCP, фоновая работа и публикация отчётов — следующие этапы.
`skill_library/*/SKILL.md` задают последовательность и требования к задачам;
для них `tools.py` предоставляет постраничный `list_files` и чтение текстовых
файлов фрагментами. Загрузка инструкции не обучает модель заново.

## Ограничения первого прототипа

- В стандартном режиме доступны `read_file(path)` и `save_report(content)`.
  При работе со скиллами доступны также загрузка инструкции, постраничный
  `list_files` и параметры диапазона строк в `read_file`.
- В стандартном режиме чтение разрешено для обычных UTF-8 файлов `.md` и `.txt`
  под выбранной папкой проекта, размером до 64 КиБ. Для обзора проекта действуют
  описанные выше правила текстовых фрагментов. Абсолютные пути, переходы `..`,
  Windows ADS, symlink/junction/reparse points и жёсткие ссылки отклоняются.
- Модель не выбирает путь отчёта. Файл создаётся исключительно в папке
  текущего запуска и не перезаписывает существующий файл. Лимит отчёта — 64 КиБ.
  Для стандартного поручения сохранение разрешается только после успешного
  чтения указанного исходного файла; пустой отчёт отклоняется.
- По умолчанию разрешено восемь запросов модели и восемь вызовов инструментов на этап,
  включая ошибочные попытки. Таймаут HTTP-запроса — 60 секунд.
- Сетевой клиент обращается только к `127.0.0.1`, `localhost` или `[::1]`.
  Прокси и HTTP-перенаправления отключены. Содержимое учебных документов
  передаётся выбранной локальной модели.
- Журнал содержит время UTC, тип события, счётчики и результат инструмента.
  Тексты поручений, файлов, отчётов, аргументы и HTTP-тела в него не записываются.
  Известный ключ API скрывается и в разрешённых метаданных.
- Содержимое файлов обозначено в инструкции модели как недоверенные данные.
  Реальные ограничения действий обеспечиваются проверками Python-кода.

Это ограничения приложения, **не системная песочница**. Они не обеспечивают
полной изоляции от другого процесса, который одновременно подменяет файлы
или каталоги. Для первых опытов используйте отдельную папку с учебными
данными. Для последующих инструментов запуска кода понадобится отдельное
проектирование изоляции.

Компоненты относительных путей с `~` отклоняются: на Windows короткие имена
NTFS 8.3 могли бы скрыть запрещённые имена файлов и папок. Это правило действует
на всех ОС, поэтому обычный файл с `~` в имени тоже не будет прочитан.

Успешное сохранение файла не доказывает, что модель правильно поняла документ.
При проверке отчёта сравните выводы с указанными источниками, особенно ограничения,
статус проекта и различие между конфигурацией и фактическим выполнением.

## Проверки

```powershell
python -m unittest discover -s tests -v
```

Тесты не требуют запущенной модели. Они проверяют границы файлового доступа,
ограничение размера, запрет перезаписи, обработку неверных вызовов,
лимиты цикла, протокол API и отсутствие содержимого/секретов в журнале.
На Windows тесты настоящих symlink могут быть пропущены, если у процесса
нет права создавать символические ссылки; проверка reparse-атрибута
и настоящей жёсткой ссылки выполняются отдельно.

Проверка с настоящей моделью остаётся отдельным шагом после её запуска.
Код возврата `0` означает штатное завершение (и наличие отчёта для стандартного
поручения), `1` — неполное выполнение или ошибку в ходе работы,
`2` — ошибку настроек или предварительной проверки API,
`130` — остановку пользователем. Наличие отчёта не является оценкой его качества.
